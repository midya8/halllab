# Every conflict, every minimal removal

[Live conflict inspector](https://midya8.github.io/halllab/conflicts.html). [Previous overlap contract](OVERLAPS.md) and [original all-different method](METHOD.md) remain in place.

## Fixed background, removable foreground

Input is the exact same bounded values/domains/scopes shape accepted by the overlap inspector: up to six variables, eight values and six distinct scopes. Each scope is all-different over its increasing list of original variable indices. **Domains are fixed background. Scopes are removable foreground.** Every subset still assigns every original variable. Removing all scopes permits repeated values, but never permits a value outside an original domain or omission of a variable. No user preference, removal cost or weighted objective is supplied.

A conflict is a scope subset with no common full assignment under the original domains. It is inclusion-minimal if every proper scope subset has a common assignment. Each reported conflict includes a first lexicographic complete witness for every single deletion. Such a witness only satisfies that conflict minus the deleted member; it need not satisfy other original scopes. Exhaustive negative counts certify unsatisfiability here, not a compact resolution proof or a claimed single Hall obstruction for several constraints.

A removal repairs the full network if the complement has a common assignment. It is inclusion-minimal if no proper removal subset repairs the network. Every repair includes its kept scope indices and first lexicographic common assignment. Restoring any one removed scope makes the kept network unsatisfiable. Each restoration includes the first bitmask-ordered minimal conflict contained in that restored active set. Adding more scopes cannot create assignments, so single-deletion/restoration checks characterize inclusion-minimality by monotonicity.

**Minimal is not minimum.** The default diamond has two triangle conflicts sharing C0. Removing C0 alone is minimal. Four size-two removals are also minimal. All five are reported, not only the smallest. A different control has a size-one global-scope conflict and a size-three pair-scope conflict, both inclusion-minimal. Fixing one conflict alone need not fix another: a valid removal must hit every minimal conflict. This is classic MUS/MCS hitting-set duality, not a discovered new theorem or a weighted optimization result.

## Complete report contract

New API `halllab.conflicts.conflicts(data)` and `verify_conflicts(report)`; separate CLI `python -m halllab.conflicts input.json --output report.json`, then `python -m halllab.conflicts report.json --verify`.

`halllab-conflicts-v1` has exactly schema,input,background_satisfiable,satisfiable,subsets,cores,repairs. Subsets are all 2^m active-scope sets in ascending numeric bitmask order, with strictly increasing original scope indices, exact solution_count and first lexicographic original full assignment, or null. Zero active scopes is first; all scopes is last. Counts range from zero to 262144. Cores are in the same bitmask order, each with scopes and deletions (removed index, remaining scopes, full assignment). Repairs are ordered by removed-scope bitmask, each with removed,kept,assignment,restorations (restored index, active scopes, contained core). Witness ties follow original increasing domain order, not scope order. Permuting scopes relabels families and ordering but preserves the underlying relations and tuple counts.

If a fixed domain is empty, even zero active scopes is impossible. The unique minimal foreground conflict is the empty set, with no deletion witnesses; no scope-removal repair exists. Its empty set cannot be hit. This explicit direct-definition extension prevents treating removal of every scope as a solution to inconsistent hard background. If the full problem is already satisfiable, there are no conflicts and the only inclusion-minimal removal is the empty set. Empty problem has one empty tuple; empty all-different scope is satisfied by it. These conventions preserve duality, including the degenerate empty families.

## Independent generation and verification

Native generator first constructs original full tuples iteratively, classifies each by the bitmask of all scopes it satisfies, and stores a histogram and first tuple per exact truth class. Counts for an active subset sum all supersets of that mask; the first common witness is the lexicographic minimum across those truth classes. Minimal families use exact immediate-neighbor counts. This is bounded truth-class aggregation, not a SAT-based MUS extraction algorithm.

The native checker never calls conflicts or subset_table. It separately replays itertools.product for every active-scope subset, tests all pairwise inequalities inside active scopes, and records independent counts/witnesses. It derives minimality by testing all proper subsets, rather than the generator's immediate-neighbor procedure. Strict recursive type/key/order equality checks every record, rejects booleans as counts/indices, missing/extra/reordered records, altered tuples and false restoration cores. Tests disable both generator entry points during verification.

JavaScript independently solves every active subset via recursive assignment search, rejecting a prefix when its assigned values already violate an active scope. It does not consume native reports or use native histogram generation. Exact complete reports are compared across engines. The browser exposes every core deletion, repair restoration, hitting-set intersection and active subset, with export and stale-report clearing. Previous two report implementations and all previous native/Node/Chrome test source files remain byte-identical; only navigation, test wiring, README and installed-reproduction wiring change.

## Boundaries

At most six scopes gives 64 subsets; at most six variables/eight values gives 262144 original tuples. Native generation stores tuples; native verification can revisit all tuples for every subset. JavaScript searches every subset separately. These bounds are not performance promises for larger instances. No scalable enumeration, incremental SAT, MaxSAT, minimum-cost repair, domain relaxation, learned model, real deployment, Z3/PySAT integration or new algorithm claim. Native strict CLI retains its existing byte/lexical JSON rules; browser JSON.parse keeps its previous last-key-wins and lexical-number differences. All controls, implementations and presentation are original; no published solver code or experimental benchmark results are copied.
