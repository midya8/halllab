# HallLab one-scope method and sources

## Exact finite contract

Input has exactly `values` (integer 0..8, not bool) and `domains` (at most six strictly increasing lists of value indices in range). Variables are positions x0 onward. Values are v0 onward. Empty scope has the unique empty assignment, hence one solution. An empty domain makes a nonempty scope unsatisfiable. These are explicit local conventions, not a claim about every solver API.

The relation is one all-different constraint: assign each variable one value from its domain, with no repeated values. Unused values are allowed. Full injective assignments equal matchings saturating all variable vertices in the bipartite value graph. An edge is globally supported precisely when it belongs to at least one such matching.

Report `halllab-v1` contains exactly schema, input, satisfiable, maximum_size, matching, solution_count, hall_sets, edges, filtered, pairwise_rounds. `matching` is a maximum-cardinality partial assignment, null for unmatched. Among maximum-cardinality assignments it is lexicographically first with integer values ascending and null after all values. The chosen matching is not the entire support relation.

For each original variable/value edge, force that variable to that value and remove that value from all other domains. A full matching of the residual graph certifies support, with the lexicographically first full assignment shown. Otherwise a Hall-deficient residual subset certifies the failure. `obstruction` contains variables, their exact residual-domain union neighbors and strictly positive deficit `|variables|-|neighbors|`. The first positive-deficit subset in increasing nonempty bitmask order is chosen, not a smallest-cardinality/minimal explanation. It may include variables unrelated to the forced variable if the original constraint was already impossible.

`hall_sets` lists every tight or deficient nonempty original-domain subset in increasing bitmask order. Tight means union size equals subset size, and is not a contradiction. Deficient means fewer neighbors than variables. Slack subsets are omitted. Edge certificates refer to forced residual domains, so their neighbor sets can differ from original `hall_sets`. No claim of minimal obstructions, enumeration of all full matchings, optimized Hall decomposition or search explanation clauses.

`filtered` retains precisely supported original values. Removing all unsupported edges simultaneously preserves all full assignments, so a second support pass cannot remove more. If the original relation is impossible, no edge has support and every filtered domain is empty.

Pairwise baseline establishes full binary arc consistency of every disequality, with synchronous updates: retain v at variable i iff each other variable j has some different value in its previous-round domain. Rounds include the original domains and one final repeated fixed point. This is not a single forward-checking sweep or a deliberately stopped baseline. Emptiness of another domain also removes every candidate. With empty scope the two empty rounds coincide; with one variable there are no binary constraints, so its domain is unchanged. This baseline can retain values even when the global all-different relation has none. Full binary AC and global domain support are different inference strengths, not different solution semantics of the decomposed relation.

## Independent implementations and audits

Native generation uses a handwritten DFS augmenting-path bipartite cardinality matcher. Each variable search has a fresh visited-value set. Repeated cardinality queries over suffix domains choose the canonical maximum partial assignment greedily. Forced-edge cardinality tests determine support. Bitmask dynamic programming counts complete injective assignments by used-value sets. Bitmask unions enumerate Hall subsets.

The native checker never calls analyze, cardinality, canonical, count_assignments, halls or pairwise. It enumerates Cartesian products of domain values plus unmatched, discards noninjective partial assignments, independently finds the best cardinality and first assignment, counts full assignments, extracts first per-edge full witnesses and enumerates subset unions using sets. It separately replays binary-AC rounds. Every value and nested key/type is compared exactly, so a boolean is not an integer index. Tests disable generator helpers while checking a saved report.

JavaScript separately explores partial assignment trees recursively and records first full support per edge, maximum cardinality and counts. It uses no augmenting-path matcher or native output at runtime. Hall unions use sets. Tests compare entire reports, not just counts or final verdicts. The browser shows original edges, assignment/partial-matching colors, forced residual obstruction text, every original tight/deficient subset, every binary-AC round, domain table, exact report and downloadable JSON. Invalid/edited input clears and disables stale output until explicit re-analysis.

Native exhaustive checks cover all 4,681 combinations of 0..4 domains over three values and all 4,096 combinations of three domains over four values, including empties. Also 120 seeded larger inputs, ten original controls, maximum 48-edge/20,160-solution scope, canonical matching, forged shape/type/witness/order, alias/immutability/idempotence and atomic CLI tests. Cross-engine tests cover 682 full reports (ten controls, 160 seeded inputs, all 512 three-variable/three-value domain graphs): 3,316 edges, 1,676 supports, 1,640 obstruction witnesses, 3,521 tight/deficient original subsets, 2,060 pairwise rounds. Actual Chrome checks all ten controls, all 90 edges (74 supports/16 obstructions), 17 original Hall subsets and 25 rounds at each of 320/390/1280 widths, plus table/graph/report/export/error clearing/overflow. These are correctness fixtures, not empirical AI performance or general proof.

## Reproduction and boundaries

Python 3.10+ standard library at runtime. `python -m unittest discover -s tests -v`. `npm test` uses Node 22 with an actual installed Chrome (`CHROME_BIN`, default google-chrome); it is not a DOM substitute. `bash tools/check_wheel.sh` builds/installs in a fresh environment and runs both CLI entry points for all ten controls, generation and verification outside checkout; confirms three module origins inside site-packages. Build tooling uses setuptools and pip. GitHub Actions tests Python 3.10/3.11/3.12/3.13 and Chrome/Node.

`python -m halllab input.json --output report.json`, `python -m halllab report.json --verify`; `halllab` is equivalent installed entry point. Native input cap 65,536 bytes, verification cap 8 MiB, duplicate keys/nonfinite constants rejected, strict shape and index types. Output uses temporary sibling file then atomic replacement; failed validation leaves existing file untouched. Browser JSON.parse has last-key-wins duplicate behavior and no native byte cap; both share finite combinatorial caps. A browser input accepting duplicate keys is not evidence of native parser acceptance.

This is an intentionally small audit reference for a classic constraint in AI planning, scheduling and assignment. It is not Régin's optimized SCC filter, Hopcroft-Karp, Choco, NetworkX or an integration with any of them. Repeated matching queries, explicit Hall subsets and Cartesian checker are intentionally more expensive than optimized propagators. No scalability claim, real scheduling deployment, learned model, paid API, runtime agent guarantee, whole-CSP solver or novel algorithm. Global support for one constraint does not ensure simultaneous satisfiability of multiple overlapping constraints.

## Sources inspected November 9, 2026

The implementation and all controls are original; these sources establish classic semantics and algorithmic context. No source code copied. Dates below are publication dates only when visible; current documentation versions can change.

1. Jean-Charles Régin, **A Filtering Algorithm for Constraints of Difference in CSPs**, AAAI 1994, primary paper. https://cdn.aaai.org/AAAI/1994/AAAI94-055.pdf. Inspected definitions of value graph/matching, Theorem 1 edge-in-saturating-matching equivalence, initialization and alternating-path/SCC discussion. Supports matching-based support, not a claim our simpler repeated-query implementation has its optimized bound. Some extracted OCR is garbled; implementation does not rely on OCR example values.
2. Willem-Jan van Hoeve, **The alldifferent Constraint: A Survey**, 2001 academic survey. https://www.andrew.cmu.edu/user/vanhoeve/papers/ercim2001.pdf. Inspected Hall Theorem 1, singleton/disequality baseline and Proposition 6 matching characterization. Hall union inequality and stronger global filtering used. Our explicit finite subset enumeration is not the survey's efficient SCC algorithm.
3. Ian P. Gent, Ian Miguel, Peter Nightingale, **Generalised Arc Consistency for the AllDifferent Constraint: An Empirical Survey**, academic empirical survey. https://www-users.york.ac.uk/~pwn503/gac-alldifferent.pdf. Inspected Section 2.2 and detailed variable-value/flow/matching/SCC examples including surplus unmatched value. Confirms full-variable coverage and that matched vital edges must not be pruned simply for crossing SCCs. No empirical runtime result from this paper is claimed for HallLab.
4. **Global Constraint Catalogue: alldifferent**, official reference catalogue, undated fetched page. http://sofdem.github.io/gccat/gccat/Calldifferent.html. Inspected purpose (distinct values), assignment/scheduling use cases and decomposition discussion. Used relation and AI context, not its specific examples, graphics or implementation.
5. **Handling constraints**, Choco-solver official documentation, undated fetched page. https://choco-solver.org/docs/modeling/constraints/. Inspected complete page: valid combinations, propagators, binary clique/table/global alternatives and forward/bounds/domain consistency distinction. Supports our propagation versus shared multi-constraint solution caveat. No Choco runtime used.
6. **networkx.algorithms.bipartite.matching**, NetworkX 3.7 official API/source documentation, undated fetched page. https://networkx.org/documentation/stable/_modules/networkx/algorithms/bipartite/matching.html. Inspected maximum-cardinality matching definition, nonuniqueness, left/right mappings and partition/disconnectedness warning. Our two partitions are explicit positions and value indices; no NetworkX code, package, Hopcroft-Karp complexity or particular match tie ordering is claimed.

Sources agree on distinct-assignment semantics, support equivalence and pairwise weakness. Optimized SCC orientation/free-node conventions vary in presentation; this project avoids transplanting an SCC recipe and instead checks each forced residual matching independently. API empty-scope semantics and canonical tie order are explicitly ours.
